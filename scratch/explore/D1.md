## Mécanisme

**Reproduction exacte** : j'ai rejoué la chaîne de `_build_masks_for_detection` hors GPU sur les 632 bulles du cache — `np.array_equal(final, det["chirurgical_mask"])` est vrai **632 fois sur 632**, 0 écart. Le modèle ci-dessous n'est pas une hypothèse, c'est le code.

### Où l'encre disparaît sur #14

| étape | px de masque | bandes x (5 tranches de 117 px) |
|---|---|---|
| `_ocr_mask_from_regions` (référence, 98 % de l'encre) | 30 708 | 13 / 6 406 / 9 442 / 9 261 / 5 586 |
| **après garde-fou `interior`** (pipeline.py:711-725) | **15 602** | 13 / 6 406 / 7 101 / 2 082 / **0** |
| après intersection `mask_binary` (pipeline.py:727-762) | 15 602 | *ratio 1.000 — aucun effet* |
| fermeture 3×3 → `chirurgical_mask` | 16 259 | 13 / 6 544 / 7 513 / 2 189 / 0 |

**100 % de la perte vient d'une seule ligne** : `bounded = cv2.bitwise_and(ocr_mask, interior)` à `pipeline.py:719`. Le masque OCR va de x=116 à x=573 ; le chirurgical s'arrête à x=429.

### Pourquoi `interior` a des trous exactement sur les lettres de droite

`TextRenderer._bubble_mask_from_image` (`core/renderer.py:2859`) ne contient l'encre **que par rebouchage topologique**. Mesuré sur #14, couverture de l'encre par chaque sous-étape :

- `similar = |gray-255| < 40` (l.2875) : **0,171** — normal, l'encre est noire
- plus grande composante connexe (l.2879-2884) : **0,000**
- `findContours(RETR_EXTERNAL)` + `drawContours(-1)` (l.2886-2890) : **0,531**

Autrement dit une lettre n'entre dans `interior` que si elle est un **trou fermé** de la zone uniforme. Et c'est là que ça casse :

| masque blanc | encre soudée à une composante noire ouverte sur le bord |
|---|---|
| `similar` brut | **0 px (0,0 %)** |
| après `cv2.erode(similar, ellipse 3×3)` | 14 655 px (47,7 %) |
| **après `cv2.erode(similar, ellipse 7×7)` — code réel, l.2878** | **21 107 px (68,7 %)** |

La cause physique, vérifiée à la loupe (`scratch/explore/d1_zoom.png`) : le texte est en **noir + liseré blanc**, et sa moitié droite est posée **sur l'arche beige**, pas sur le blanc du ballon (médiane du fond par bande : 255 / 255 / 255 / **195** / **132**, alors que la fenêtre est ref=255 ±40). À droite, le seul blanc autour d'un glyphe est son propre liseré : **rayon médian 2,0 px** (2,8 px à gauche). L'érosion de 3 px l'efface entièrement → le corps noir de la lettre fusionne avec l'arche → l'arche touche le bord du crop → ce n'est plus un trou fermé → `RETR_EXTERNAL` ne le rebouche pas → hors de `interior` → l'encre est retirée par le `bitwise_and`. La décroissance progressive suit simplement la diagonale de l'arche qui balaie les trois lignes de texte.

### Le garde-fou qui aurait dû rattraper le coup

`pipeline.py:724` : `if count(bounded) >= 0.5 * count(ocr_mask)`. Ici **15 602 / 30 708 = 0,508**. Il passe avec **248 px de marge, soit 0,8 % de l'encre**. Sous 0,5, le masque complet aurait été gardé et l'effacement aurait été correct. Ce cas est littéralement à pile ou face.

## Structurel, pas paramétrique

Aucun réglage ne rattrape le cas :

| variante | couverture de l'encre |
|---|---|
| code actuel | 0,508 |
| tolérance 40 → 60 / 80 / 100 | 0,609 |
| tolérance → 127 (= plus de seuillage utile) | 1,000 |
| noyau d'érosion 7×7 → 3×3 | soude déjà 47,7 % de l'encre |
| **suppression de l'érosion** | **0,994** |
| **`MORPH_CLOSE 31×31` avant l'étiquetage au lieu de l'érosion** | **0,997** |

Le défaut est **structurel** : `_bubble_mask_from_image` a été écrite pour son autre appelant, `insert_text` (`core/renderer.py:697`), où — sa docstring le dit l.2864-2867 — *« insert_text reçoit l'image DÉJÀ détourée, donc l'intérieur du ballon est uniforme »*. Là, il n'y a plus de glyphes, donc le rebouchage de trous ne joue aucun rôle et l'érosion est inoffensive. `pipeline.py:711` la réutilise sur le crop **original, texte présent**, où c'est précisément le rebouchage qui décide si une lettre est effacée ou non. Toute lettre à moins de ~3 px de la frontière de la zone uniforme est perdue.
